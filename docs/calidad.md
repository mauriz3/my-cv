# Calidad: tests, cobertura, accesibilidad y Lighthouse

Los tres corren en cada PR y en cada push a master; axe y Lighthouse usan el sitio que genera `verify` (artefacto `site`, sin segundo build), servido en local con `scripts/serve-static.mjs`. Ese servidor imita a Netlify en lo que importa (`/ruta` → `ruta.html` o `ruta/index.html`, 404 con `404.html` y las cabeceras de `_headers`, CSP incluida, así una CSP rota también se detecta), comprime el texto con Brotli como Netlify (sin eso Lighthouse mediría entre 6 y 8 veces más bytes de HTML y CSS que en producción) y responde `/geo` con la Edge Function real (`netlify/edge-functions/geo.ts`) y un país simulado (`GEO_COUNTRY`, por defecto `ES`: el aviso aparece, como para una visita de la UE). No envía `X-Robots-Tag`: fuera de producción el build lo añade a propósito y Lighthouse lo contaría como fallo de SEO (el artefacto de producción no lo lleva; lo comprueba `deploy-production`).

- **Accesibilidad (job `a11y`)**: `tests/a11y/axe.spec.ts` (`@axe-core/playwright`, reglas WCAG 2.2 A/AA y best-practice) sobre `/en/`, `/es/`, `/en/visits` y `/en/privacy` en tema oscuro y claro (`localStorage["nuxt-color-mode"]`), con movimiento reducido para medir el estado final y no un fotograma de animación. **Falla con violaciones serious o critical**; las moderate/minor se listan en el log. `/en/books` se audita dos veces: el destino tras el salto (`/en/#books`, en ambos temas) y la página mínima en sí (se le quitan solo el meta refresh y el script del salto para que no navegue). El aviso de analítica solo existe en el build de producción, así que se audita en los push a master, no en las PR.
- **Lighthouse (job `lighthouse`)**: `@lhci/cli` (versión fija vía `npx`, fuera de `package-lock`) con `lighthouserc.cjs`: 3 pasadas (mediana) en `/en/`, `/es/`, `/en/visits` y `/en/privacy`, preset móvil por defecto. Umbrales: rendimiento ≥ 0,85, accesibilidad ≥ 0,95, buenas prácticas ≥ 0,9, SEO ≥ 0,95. `/en/books` no entra: redirige en cliente a `/en/`, que ya se mide. Sin servicio externo: informes en `lighthouse-report/` (`upload.target = filesystem`). Dos perfiles, según el país de `/geo`:
  - `npm run lighthouse` (siempre): visita de fuera de la zona con aviso (`US`). **Todos los umbrales fallan la CI.**
  - `npm run lighthouse:consent` (solo en push a master, el único build con Google Analytics y aviso): primera visita desde la UE (`ES`), con el aviso en pantalla. Accesibilidad, buenas prácticas y SEO fallan la CI; **rendimiento solo avisa** (informes en `lighthouse-report-consent/`, mismo artefacto).
- **Por qué el rendimiento con aviso no bloquea** (decisión de noviembre de 2026, tras el primer push a master con Lighthouse): el aviso es `client-only` y aparece cuando la app ha hidratado y `/geo` ha respondido (está oculto hasta saber el país, para no mostrarlo a quien no le corresponde). Como es el texto más grande de la pantalla, pasa a ser el LCP aunque el contenido ya esté pintado: en local, con el build de producción, LCP 4,5–4,6 s y rendimiento 0,81–0,83 en `/en/`, `/es/` y `/en/visits` (sin aviso: LCP 0,9–1,0 s, rendimiento 0,96–0,99). Bajarlo exige cambiar el diseño del aviso (prerenderizarlo visible y ocultarlo después fuera de la UE, lo que lo haría parpadear al resto), así que queda medido y visible, pero sin bloquear el despliegue, hasta que se decida. El resto de categorías sí se exige con el aviso: por ejemplo, su enlace a privacidad tiene un texto descriptivo («Detalles de privacidad» / "Privacy details") porque «Más información» suspendía la auditoría `link-text` de SEO.
- **Cobertura (en `verify`)**: `npm run coverage` (`@vitest/coverage-v8`, misma versión que vitest) sustituye a `npm run test`. **Umbral bloqueante: 80 %** en líneas, sentencias, funciones y ramas (`coverage.thresholds` en `vitest.config.ts`). Cuenta todo el TS/JS propio de `app/composables`, `app/utils`, `lib/`, `data/`, `server/`, `netlify/` y `scripts/`, lo carguen los tests o no. Fuera, por no ser código propio de la app: tests, configuración (`*.config.ts`, `app/app.config.ts`), lo generado (`.nuxt/`, `.output/`) y `node_modules/`. Los `.vue` (componentes y páginas) aún no entran; los cubren axe y Lighthouse. La tabla sale en el resumen del job (`scripts/coverage-summary.mjs` → `$GITHUB_STEP_SUMMARY`).
- **Dos proyectos de Vitest**: `unit` (`tests/unit/`, Node: lógica pura, datos, funciones de Netlify, ruta de Nitro y scripts) y `nuxt` (`tests/nuxt/`, entorno Nuxt de `@nuxt/test-utils` con happy-dom: composables con auto-imports, i18n y ciclo de vida). Los scripts de `scripts/` exportan su lógica y solo actúan al ejecutarse con `node` (`scripts/isDirectRun.mjs`); el PDF separa la CLI (`generate.ts`) de la lógica (`render.ts`).
- **Ver los informes**: en GitHub → Actions → la ejecución → *Summary* (tabla de cobertura) y, abajo, *Artifacts*: `coverage` (abre `index.html`), `lighthouse-report` (un HTML por pasada y `manifest.json` con las puntuaciones; en push a master también `lighthouse-report-consent/`) y `a11y-report` (informe HTML de Playwright). Se guardan 7 días.
- **En local**: `npm run generate` y después `npm run test:a11y` o `npm run lighthouse` (levantan el servidor solos en el puerto 4173; necesitan Google Chrome instalado). Para reproducir un push a master: `CONTEXT=production npm run generate` y después `npm run lighthouse` y `npm run lighthouse:consent`. Informes: `playwright-report/` (`npx playwright show-report`), `lighthouse-report/` y `coverage/index.html`.
